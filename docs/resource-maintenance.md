# 资源到期维护与健康检查

2026-09-11 · P7 本地增量 · 固定点 `8b0e95c`。本批补齐维护执行回执与独立健康检查，**没有安装持续调度或告警服务，没有启用真实资源服务**。完整 P1–P9 仍进行中。

## 已实现

维护者可以区分从未运行、最近成功、最近失败、长时间未成功，以及当前到期积压。数据仅包含计数、时间、处理账号数、状态和 SQLSTATE；不记录用户 ID、目标、字幕、笔记或错误正文。

- `private.run_resource_maintenance()` 包装现有到期扫描，按 1–1000 个账号限批，默认 100。保留蓝图优先加锁、跳过忙碌账号、整链清理和单次退款规则。
- 事务级 advisory lock 阻止多个维护批次同时执行。忙碌返回 `busy`，不会冒充成功或覆盖最近回执。
- 扫描异常会回滚该批已发生的清理和退款，再保存失败代码。成功清理不会误删除正式蓝图、绑定或用户学习历史。
- 私有单行状态只保留最近结果、最近成功时间和成功／失败累计数，不建立无限增长的业务日志。失败批次的处理数量为未知，不报告为零或部分成功。
- `private.resource_maintenance_snapshot()` 独立统计当前已到期、未清理、具有可信策略的检索根记录及最早期限。积压数量不是上次处理账号数，也不是所有数据库副本总数。
- 两个入口都以调用者权限执行；匿名、登录用户及 worker 的 `service_role` 均无权限。没有新增公开 RPC、Edge 入口或客户端密钥。

旧记录没有可信期限时不会被此扫描自行删除，仍需另行盘点和明确删除决定；到期访问限制不依赖健康检查。[期限机制](resource-evidence-expiry.md)与[主动清理](resource-evidence-clearing.md)的边界保持不变。

## 独立检查，而不是只看定时任务显示成功

[健康检查 CLI](../scripts/resource-maintenance-health.mjs)只读取 stdin 中的数据库聚合快照，不连接数据库、不持有凭据、不发送网络请求、不执行清理。它强制要求显式设置两个容忍窗口，使用快照的数据库观测时间计算年龄，不与运行机器的绝对时钟相减。

输出只有固定聚合字段；拒绝额外字段、畸形状态、超过 8 KiB 的输入和错误参数，不回显输入或错误详情。退出状态：

| 退出码 | 含义 |
| --- | --- |
| 0 | 最近成功且积压年龄未超过配置；不保证积压为零 |
| 1 | 从未运行、最近失败、成功过旧、积压过旧或时间关系矛盾 |
| 2 | 输入或参数无效；不能当作健康 |

本地只读检查示例，300／120 秒仅是演示值，不是产品清理 SLA：

```bash
set -o pipefail
bash scripts/with-m1-runtime.sh docker exec -i supabase_db_blueprint-local \
  psql -X -qAt -v ON_ERROR_STOP=1 -U postgres -d postgres \
  -c 'select private.resource_maintenance_snapshot();' \
  | bash scripts/with-m1-runtime.sh node scripts/resource-maintenance-health.mjs \
    --max-success-age-seconds 300 --max-overdue-seconds 120
```

部署方必须给整个数据库查询／CLI 进程设置外部超时，并把退出 1、2、查询失败和超时都接到告警；CLI 不会凭空知道数据库不可达或上游永久不结束。不要把管理凭据放入应用，也不要把任意用户数据送入该输入管线。

被捕获的 SQL 失败会正常返回失败回执，所以 pg_cron 的任务状态可能仍显示 `succeeded`。需要读取维护快照判断；连接终止、查询取消、事务整体回滚等也可能无法保存失败，最近成功年龄是另一条检测路径。单行回执不是可靠审计历史，较后的成功可能覆盖某次失败，累计失败数仍保留；有历史告警需求时应由运维采集器保存这些无正文指标。

## 上线顺序与尚未完成的能力

1. 先核清[内容权限与保留策略](resource-retention-research.md)，确认目标数据库的增量迁移和受管理账号范围。没有策略不应开启真实检索。
2. 在目标环境由维护者选择批量、频率、成功年龄／积压容忍窗口和外部查询超时，指定值班责任人与告警去向。不能照搬本地一秒夹具窗口。
3. 明确安装持久调度，调用本批包装入口而不只调用旧扫描函数；否则不会更新维护回执。独立健康检查不能与被监控任务共用唯一触发器，否则任务停运时检查也消失。
4. 在目标环境演练停运、积压、锁竞争、失败和恢复，并验证旧客户端／数据库／worker 的协调升级，之后才能考虑开放服务。

迁移本身不创建定时任务。pg_cron 同名 `schedule` 会更新现有任务，运维启用前必须检查既有作业，不能盲目覆盖；移除时按精确作业 ID 操作。不要用卸载扩展停止单个任务，因为这会删除所有 cron 作业。相关依据：[Supabase Cron](https://supabase.com/docs/guides/cron)、[调度与取消](https://supabase.com/docs/guides/cron/quickstart)、[安装与卸载](https://supabase.com/docs/guides/cron/install)。

本批不会提供授权期限的法律判断，不清理处理商、数据库日志或备份，不覆盖账号整体删除，也不实现来源刷新／下架检测。数据库自身日志与 cron 历史的留存仍须单独管理；应用单行状态不等于整个基础设施不会产生日志。

## 本地验证

实现前先复现不存在的维护入口、CLI 接受损坏快照和未来时钟误报健康，再逐项修复。

- 新增 42 项数据库行为检查：成功、失败回滚、恢复、限批、退款一次、无正文诊断、单行状态及三种应用角色拒绝。
- CLI 四组真实进程测试覆盖健康、畸形／超量输入、显式阈值、失败／积压／陈旧、时间矛盾和无正文回显，已接入 `check:m1`。
- 主线程双连接实际演练：两个一次性账号到期后 CLI 告警；advisory 锁忙碌不改回执；锁住其中一个蓝图后扫描跳过该账号并清理另一个，解锁后补清理，CLI 恢复健康。
- 临时 pg_cron 一秒任务实际调用维护包装入口，清理第三个到期夹具；核对数据库快照与 CLI，再取消精确作业并等待在途运行结束。三个测试身份已删除，作业不存在，没有留下持续调度。
- 增量升级逐行保留既有业务表，既有私有函数 OID、函数体、权限和安全模式不变，仅增加空状态表与两个入口。实际执行计划复用既有 `resource_due_content` 索引，没有重复创建索引。
