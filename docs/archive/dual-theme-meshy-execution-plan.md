## 1. 目标、现状与范围

为 Blueprint Web 主页制作两套完整的沉浸式场景：男性主角的赛博义体诊疗室，以及东方女性剑客坐在湖中小舟上持剑的武侠场景。镜头固定构图，支持轻微指针视差。保留目标选择、当前行动、学习证据、导航及主题偏好的业务语义。

本次明确采用以下分工：**Codex 生成图片并组织选样 → 用户确认 → Meshy 制作复杂 3D 资产 → Codex 用本地代码组装、制作微动作和后处理 → 浏览器验收。**

已确认的约束：

- 两位角色均为原创基础角色；不要求复用旧角色或真实人脸。赛博角色为成年男性，武侠角色为成年东方女性。
- 人物细节与最终提示词在图片阶段共同确定；不能把本文中的初始美术方向当作已批准的样式。
- 必须先生成候选图，由用户选择、修订，再批准最终的单资产参考图。未通过图片审查的资产不得送入 Meshy。
- 暂不安装 Blender。首版不包含自由探索、战斗、拔剑、复杂布料模拟或完整角色编辑器。
- Meshy 总预算上限为 600 credits；这是规划边界，不是本轮提交付费任务或自动返工的授权。
- 用户已要求实施本计划，并授权使用 Meshy 推进；当前完成到人物灰模／减面审查节点。后续按模型、姿态与浏览器验收条件逐步推进，本轮未改变生产界面、提交或发布代码。

## 2. Codex 与 Meshy 的职责

| 环节 | 执行方 | 做法与边界 |
|---|---|---|
| 整景候选、配色、光照变化 | Codex 图像工具 | 展示候选、局部编辑、记录选择；不调用 Meshy 图片接口 |
| 人设、道具、建模参考图 | Codex 图像工具 | 基于已选样式生成干净单资产图；保留同一主体特征 |
| 多视角图 | Codex 图像工具＋人工审查 | 检查服装、义体、配件、左右关系是否一致；不假设多张图天然一致 |
| 页面构图预览 | Codex 本地代码 | 将图片与真实 HTML 面板叠合，检查可读性和遮挡 |
| 简单场景几何 | Codex 本地代码 | 墙、地面、灯带、屏幕、简单线缆、湖面等程序化制作 |
| 复杂网格 | Meshy | 人物、诊疗椅、工作台、机械臂、木舟、剑等逐资产生成 |
| 重网格化／减面 | 首版保留 Meshy | 压缩不等于重拓扑；不承诺本地压缩能解决不良变形拓扑 |
| 角色与复杂道具纹理 | 首版保留 Meshy | 生成适配网格 UV 的纹理；普通纹样图片不能直接替代完整贴图流程 |
| 自动骨骼绑定与蒙皮 | Meshy | 本地检查并调整姿态；不把骨骼变换代码等同于自动权重制作 |
| 人体预设动作 | Meshy 按需 | 先验证需要的坐姿／待机动作；不为不会使用的动作付费 |
| 船体、灯光、设备、微动作 | Codex 本地代码 | 关键帧、骨骼小幅修正、材质和着色器动画 |
| 泛光、雾、水面、视差 | Codex 本地代码 | 使用现有 Three.js WebGL 渲染路径 |
| 压缩、资源管理、网页接入与验收 | Codex 本地工具 | 下载后检查、纹理缩放、适用的压缩、加载与资源释放测试 |

### 2.1 图片工具与“本地”的含义

默认遵循已安装的 `imagegen` Skill，使用 Codex 内置图像生成／编辑工具，不调用 Meshy 的 `text-to-image` 或 `image-to-image`。图片由图像服务生成，最终批准文件保存到项目；不是图像模型在本机 GPU 上离线推理。Codex 图像用量单独记录，不计入 Meshy credits，也不描述为无限免费。

当前内置工具没有模型选择参数，不能承诺固定为用户提到的“GPT Image 2.5n”。官方公开文档列出的相关型号包括 `gpt-image-2.5-sunburst` 和 `gpt-image-2.5-flare`，但 API 型号可用不代表当前内置工具允许指定。先按内置图像能力执行；若后续明确要求锁定具体 API 型号，另行核实接口、凭据与费用，不静默切换到独立 API。

## 3. 两套场景与初始资产预算

### 3.1 赛博朋克：义体诊疗室

成年男性主角置于有使用痕迹的义体诊疗空间。人物与义体的细节共同确定；空间参考义体医生诊所的气质，以工作台、诊疗椅、设备和局部屏幕光建立叙事。

首轮提供三种可选方向，保持角色与场景主题不变：

1. 冷色诊疗室：青蓝工作灯与少量暖色指示灯，突出人物轮廓。
2. 地下维修诊所：暖工作灯与冷屏幕光混合，突出旧金属和生活感。
3. 街边霓虹诊所：窗外城市灯光进入室内，突出空间纵深。

角色默认在设备旁站立待机，位置随选定构图确定。功能面板占用画面安静区域；设备屏幕只承载装饰信息，真实任务内容使用 HTML。首版机械臂可以整体小幅转动，不假设生成网格已经拆分为可独立驱动的关节。

### 3.2 武侠：湖舟女剑客

成年东方女性剑客坐在船头附近的横座上持剑，小舟、人物和剑形成稳定重心。按用户最新 v2 成图，首版采用交叠双腿的固定坐姿，较长的带鞘剑斜横置于腿上；不增加换腿、盘腿、起身、拔剑和挥剑动作。姿态校准重点检查髋膝、靴子、衣摆以及双手与剑的接触关系。

首轮提供三种环境候选：

1. 月下静湖：月光、水面反光和少量暖色点缀。
2. 晨雾湖面：浅色雾气与远山层次，整体轻盈。
3. 暮色烟波：夕照与冷色湖面相接，突出人物剪影。

服装既要保持武侠气质，也要适合坐姿变形。选样时检查袖口、下摆、头发与握剑关系；不以站姿图代替坐姿评审。若长衣摆无法可靠变形，先展示局部服装修订供用户选择，不擅自把角色改为站姿。

## 4. 分阶段执行与审查节点

### P0：建立简报与制作目录

先为两个主题分别整理场景、人物、材质、构图、光照、禁止变化项，以及需要用户选择的细节。记录角色设定、图片版本、选择结果和提示词；一个角色的后续图片持续引用其批准版本。

制作目录约定（未来执行时创建）：

```text
art/dual-theme/
  decisions.md                 # 用户选样、修改要求和批准记录
  cyberpunk/concepts/          # 整景候选
  cyberpunk/references/        # 角色和道具图
  eastern/concepts/
  eastern/references/
  meshy/                      # 任务快照、母版、下载模型与纹理
  manifests/                  # 资产来源、版本、成本和检查结果
```

同名资产采用版本化文件名，禁止用新候选覆盖批准版本。制作母版不直接放入网页公开目录；最终网页资源在集成阶段放入 `apps/web/public/assets/themes/<theme>/<version>/`。未经批准的候选不进入生产发布包。

### P1：Codex 整景出图与第一次选样

每个主题首轮三张，共六张。先共同完成两个主题的提示词，再调用内置图像工具。每张图单独生成和编号；比较时展示整图，并叠加功能面板布局示意，保持场景审查和文字可读性审查同时进行。

用户分别选中一个方向，说明保留项和修改项；后续只对选中方向做有目的的局部编辑。避免每次修图都重新设计人物、构图和全部道具。

**通过条件 A：** 用户批准两套场景的整体方向、构图和主要人物轮廓。未通过时停留在 Codex 图片阶段，不提交任何 Meshy 3D 任务。

### P2：Codex 单资产参考图与第二次确认

从批准概念中提取七件资产的独立设计，每件至少一张干净建模参考图；两个人物各准备一张补充视角。预计九张是初始数量，不要求为了凑数生成没有用途的视图。

角色必须区分：

- 展示姿态图：用于评价主页效果；武侠必须展示坐舟持剑。
- 建模参考图：完整身体、四肢分离、A/T 姿态、无遮挡、适合自动绑定；武器与人物分开。

单资产图要求主体完整、背景简单、轮廓明确，避免强景深、强遮挡、夸张透视和将灯光高光误认为材质。不同视角必须保持脸、服装、义体位置和配件一致；发现矛盾时修图或只使用可靠的单视角，不把矛盾视图一起提交。多视角拼图须拆成独立图片并逐张审查，不能直接当作一个物体输入。

**通过条件 B：** 用户批准具体图片版本及其资产对应关系。登记文件路径与哈希；后续 Meshy 请求只引用这些版本，不上传整个候选目录，不把整景直接生成成不可分离的人、船、剑组合。

### P3：先验证武侠坐姿与持剑

这是最先实施的 3D 小样，不与其余模型批量并行提交。

1. 用批准的女性角色建模图生成无纹理灰模，检查人体、脸、手和服装轮廓。
2. 灰模通过后重网格化到预算，检查实际三角形数，再制作纹理。
3. 对适合绑定的带纹理类人模型自动绑定；下载真实模型和骨骼结果。
4. 先用本地简化船座和剑占位物验证骨骼、坐姿与挂点，再制作正式木舟和剑。
5. 优先试验动作目录中的 `Chair Sit Idle Female`（本次只读查询为 action_id 32；执行前复核目录）。这是试验候选，不是已经适配的动作。
6. 建立骨骼映射，校准座高、臀部、腿部、手腕和握剑角度。动画更新后应用必要的姿态修正，剑安装到手部挂点。

坐姿预设不适合时，在同一个已绑定角色上尝试本地固定坐姿与小幅呼吸、转头动画。若网格或权重导致持续明显穿插，回到对应服装／网格阶段局部修改；不继续购买无关动作，也不以改相机隐藏全部问题作为通过依据。

**通过条件 C：** 在允许的镜头范围和完整循环中，角色稳定坐在横座上，剑不漂移，腿部、袖口、下摆和座位没有明显穿插。记录用户审查结果后再扩大制作范围。

### P4：完成剩余模型与必要动作

制作赛博角色及剩余道具，遵循“批准参考图 → 灰模审查 → 减面 → 纹理”的顺序。绑定只用于人物，不为静态道具添加无用骨骼。角色与道具都需检查实际 GLB，缩略图只能证明其可见外观，不能证明拓扑、权重或文件结构合格。

人物预设动作最多预算四个，按真实需要逐个选择。不要因为绑定结果包含行走／跑步就把它们放进静态主页；也不要把完整动作包当作首版必需品。

### P5：本地场景、动作与后处理

使用现有 Three.js／React Three Fiber 的 WebGL 路径。镜头固定，指针只带来小范围偏移并平滑回中；触屏不引入自由旋转手势。人物点击反馈增加冷却，避免动作堆叠。

| 层级 | 赛博朋克 | 武侠 |
|---|---|---|
| 人物待机 | 呼吸、细小重心变化 | 坐姿呼吸、轻微头部变化 |
| 人物点击 | 看向镜头或轻微点头 | 小幅转头或点头，维持握剑 |
| 环境动态 | 指示灯、屏幕扫描、设备缓慢转动 | 船体升降与摇摆、水波、缓慢薄雾 |
| 目标选择反馈 | 面板及局部灯光短暂强调 | 面板及局部水光短暂强调 |
| 泛光 | 局部屏幕、灯带、义体发光 | 极轻微的月光／水面亮部 |
| 色彩 | 冷暖分区，限制霓虹过曝 | 柔和对比，保持肤色自然 |

船、人物和剑放在同一船体运动层级内，再运行人物内部动画，避免船动人不动。水面先用法线扰动、反射近似和局部波纹，不依赖昂贵的实时平面反射。

后处理优先使用 Three.js 自带的 EffectComposer、RenderPass、UnrealBloomPass 与 OutputPass，正确处理线性颜色、色调映射和输出转换，避免双重转换。Bloom 以发光材质和阈值控制；HTML 不进入后处理画面。首版不启用重度景深、动态模糊、频闪或明显色差。

本阶段不调用 Meshy。Meshy 动画接口的帧率、格式等后处理不负责网页中的泛光、雾或水面。

### P6：开发预览、主页接入与最终验收

先新增仅开发环境可用的场景预览入口，再接入正式主页。批准前保持现有生产资源。示例数据与私人目标严格分离，不把概念图中的虚构内容写入账号。

通过视觉、行为和性能检查后，将批准资源以版本化清单接入主页。保留静态海报与现有 DOM 作为降级路径，回退只需切回已通过版本或关闭 3D，不影响目标系统。

## 5. 工具执行与预算

### 5.1 已安装工具的使用约定

本会话已经安装官方 Meshy Skill、CLI 0.3.0 和 MCP 0.5.1；这不代表本计划已开始生成。执行时先核实工具版本、认证和所需命令帮助。

根据 `meshy-3d-generation` Skill，API、上传、下载和 Meshy 网格操作通过 CLI 完成；MCP用于适合的查询与工具协作。业务命令使用 `--output-schema v1 --format json --no-update-check`，写入命令明确 `--workspace`。当前版本没有暴露的参数，必须先核实，不假定最新 API 的全部能力已被安装版本支持。

每个收费任务 `create --async` 只提交一次，保存资源类型和任务 ID，再用对应 CLI `wait`。超时继续查原任务，禁止把超时当作重新创建的理由。及时下载需要的 GLB、纹理与动作，记录实际 `consumed_credits`；缺失时记“未知”，不猜为零。

凭据沿用已经配置的本地读取方式，不写入图像、提示词、文档、前端或资源清单。不在产品运行时请求 Meshy，不新增面向用户的 3D 计费生成服务。

### 5.2 新版 Meshy 积分估算

依据 2026-09-20 核对的 [Meshy 官方 API 定价](https://docs.meshy.ai/en/api/pricing)。采用标准几何生成，不选择高几何分辨率附加费或 8K 纹理；执行前复核所选模型与参数。

### 5.3 成本优化顺序

优先通过图片修订减少错误生成，其次减少不需要的资产和动作，再检查是否能以简单几何代替道具。不要为了节省单次积分而牺牲人物坐姿稳定性，也不要将压缩、减面、重拓扑混为一谈。任何压缩或纹理优化都必须复查外观、骨骼、动作与加载兼容性。

## 6. 网页接口与运行约束

新增 Web 内部的版本化场景清单，最少描述：主题标识、海报、模型资源、变换、动作映射、道具挂点、镜头、灯光、效果参数及质量档位。路径只来自受控清单，不提供任意远程模型执行入口。

- `cyberpunk`、`eastern` 标识及账号偏好接口保持不变；无需数据库迁移。
- 背景 Canvas 与 HTML 功能层分离；目标、行动、证据和导航继续使用现有业务数据。
- 主题变化只替换场景，不以主题为 key 重挂业务子树，不重置选中的目标、输入和滚动状态。
- 每次只加载当前主题的 3D 资源。快速切换时忽略过期加载结果并释放不再使用的纹理、几何体、动画混合器和监听器；共享资源按所有权管理，不能提前释放。
- 3D 模块保持在 Web 应用内，不进入扩展共享 UI 包。
- 首屏先呈现功能面板与海报；失败时保留可操作页面，不把整个主页卡在模型加载状态。
- 小屏默认静态或 2.5D 场景；桌面提供降低画质及关闭动态的方式。
- `prefers-reduced-motion` 下停止视差、循环动作、船体摆动和装饰动画；后台页面停止不必要的持续渲染。

## 7. 验收矩阵与工程验证

### 7.1 美术与动画

| 检查项 | 通过条件 |
|---|---|
| 图片选样 | 两个整景方向和七件资产的实际输入版本都有明确记录 |
| 风格一致 | 角色、服装、道具、场景和面板属于批准的视觉方向 |
| 模型外观 | 在完整模型及有限视差可见区域检查，不仅看缩略图 |
| 坐姿与持剑 | 循环中无明显船座穿插、握持漂移、手腕扭曲和衣摆拉伸 |
| 其他动作 | 无脚滑、肢体拉伸、切换跳变或连续点击堆叠 |
| 场景动态 | 船与人物同步；光效不过曝、不妨碍阅读 |
| 最终确认 | 用户批准真实浏览器场景；概念图通过不等于 3D 通过 |

### 7.2 行为与可访问性

覆盖两主题的目标选择、当前行动、导航、证据、空目标、认证失败和业务加载失败。检查键盘操作、清晰焦点、44 CSS px 触控目标及 WCAG 2.2 AA 对比目标。检查模型失败、WebGL 不可用、上下文丢失恢复、快速主题切换和减少动态效果；所有情况下核心 HTML 功能保持可用。

### 7.3 性能目标（待实测）

- 桌面常规档接近稳定 60 FPS，低档目标 30 FPS；实际结果标注分辨率、DPR、浏览器、硬件、质量档和采样时段。
- 每主题可见三角形初始上限约 100,000；同时控制 draw calls、材质数量、透明层叠和纹理显存，不能只报告面数。
- 每主题首次 3D 传输目标不超过 10 MiB；超出先优化纹理和重复资源，不以无提示长时间加载作为解决方案。
- 检查 390px、768px、1440px 宽度和主题连续切换后的资源增长。窄屏内容不被人物或船体遮挡。
- 软件渲染截图仅作为视觉证据；帧率与显存结论来自真实硬件浏览器。记录首次加载和稳定运行两类数据。

本次是文档任务，由主 Agent 完成，不启动子智能体。未来获准编辑产品代码时重新按仓库协议分级，先冻结独立行为验收契约，再建立相应失败测试和实现；不把本计划的写作当作已完成测试契约。
